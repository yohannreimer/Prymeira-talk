## Approved behavior and semantics

1. First confirmed Calendar booking in a native CTWA conversation creates Schedule. Reminders, slot offers, failure/unavailability, manual tags, cancellation, rebooking and repeated processing never create extra meeting conversions. One meeting milestone per workspace/conversation. This marks booked, never attended or qualified by inference.
2. Owner-only Confirmar venda form on the selected native CTWA conversation asks for a required sale reference and a positive BRL value. It does not mark an actual sale until submitted. Reference is immutable and unique across the workspace, including channel changes; same reference/value/origin retries return the original receipt. Changed value/currency/origin is a conflict, not a second sale or mutation. Multiple genuinely different sales can be recorded.
3. Enable lifecycle with optional lifecycleEnabled boolean, default false, plus a required activation epoch lifecycleEnabledAt when enabled, inside the existing exact-workspace CTWA_TRACKING_CONFIG entry. Feature hidden and writes denied outside enabled workspace/owner; all auto-capture and forwarding gates enforce the same scope server-side. Existing LeadSubmitted stays active independently. No new secret or pixel; existing HMAC/Meta config is reused.
4. Existing Tracking remains sole Meta sender, with durable pending→sending CAS and terminal accepted/rejected/unknown fences. Retries Talk→Tracking preserve stable IDs and immutable facts and never imply retrying Meta after an uncertain outcome.
5. Lifecycle is attached to the original lead in the dashboard, never added as extra lead rows or visits/GA4/website purchases. Show actual per-stage statuses and purchase values; never infer accepted from preparation or sending.
6. Only future confirmed actions are captured. Do not book a real meeting, create a real sale or resend the accepted lead to validate. Use isolated fixtures/mocked Meta (or explicitly marked Meta Test Events only if justified); first real lifecycle Meta acceptance remains pending until a real stage happens.

## Contract

- Existing version 1 LeadSubmitted envelopes, signature derivation namespace, route and identities remain byte-compatible.
- Version 2 uses existing base scope/native/contact fields, eventName Schedule or Purchase, leadEventId, sourceReference (64 lowercase hex hash, not Calendar URL or message contents), and Purchase-only purchase {orderId, valueCents, currency}. currency BRL for the manual UI. orderId matches existing safe reference pattern [A-Za-z0-9._:-]{1,128}; valueCents positive safe integer, at most 100000000000000.
- leadEventId is the stable existing LeadSubmitted ID of the persisted attribution. Tracking requires a matching scoped original lead row; missing dependency returns retryable failure before Meta. Verify workspace/channel/conversation/message/attribution against that original row, not just event ID.
- Schedule event ID uses existing stableCtwaEventId with name Schedule, businessKey once. Purchase uses Purchase and hash(orderId). sourceReference is hash(Calendar event ID) for Schedule and hash(orderId) for Purchase. All lifecycle business fields join the immutable identity; contact presentation remains frozen first-write as in version 1.
- D1 lifecycle schema includes event_id primary key, original lead ID/scope/native fields, event_name CHECK Schedule/Purchase, source reference, identity hash, immutable time/contact, purchase fields with conditional checks, Meta state/status/numeric diagnostics and timestamps. Unique meeting milestone scoped to workspace/conversation; unique purchase reference/hash scoped to workspace (not channel). Validate shape, bounds and cents before D1/network. Do not return raw native click IDs/credentials.
- Purchase Meta custom_data includes value=valueCents/100 and currency BRL; use a stable scoped opaque order identifier. Schedule sends no purchase money. Names/phones follow existing hashing and first-write presentation. Retain API v25; do not make unrelated upgrades.
